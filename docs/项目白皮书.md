# RD STUDIO 项目白皮书

> 版本：2026-07-12 现状基线
>
> 适用对象：社团负责人、产品维护者、前端开发者、数据库管理员和后续接手成员

## 1. 项目使命

RD STUDIO 社团网站用于承载游戏开发社团的公开展示、内容发布、成员协作和长期知识沉淀。它不是单纯的宣传页：公开访客可以了解和阅读内容，注册用户可以参与互动，社员可以访问内部资源，管理员可以完成内容与资料审核。

项目希望解决四类长期问题：

1. **对外表达**：集中展示社团定位、成果、文章和公开知识。
2. **内容协作**：让成员提交文章、参与互动并申请进入知识库。
3. **权限隔离**：公开内容、成员资料和内部资源按角色安全分层。
4. **组织传承**：把数据结构、运行方式、维护流程和关键决策留在仓库中，而不是依赖某一个人的记忆。

## 2. 产品边界与成熟度

当前项目处于“安全与工程基线重建”阶段。数据库基线、主要 RLS、官方 Supabase 客户端和统一认证状态已经逐步建立；领域 service、统一错误模型、完整自动化测试和正式视觉系统仍在后续 Task 中。

| 状态 | 含义 |
|---|---|
| 已实现 | 仓库存在运行代码或迁移，并有相应构建/测试记录 |
| 重构中 | 旧页面可存在，但正在迁往统一基础设施，需查看 DevPlan |
| 规划中 | 只有设计或 Task，不应对外承诺为可用能力 |

`DevPlan/` 是唯一任务状态入口。任何文档中的愿景都不能代替 Task 的 `DONE` 与验证记录。

## 3. 用户与角色

| 角色 | 主要能力 | 权限来源 |
|---|---|---|
| 访客 | 浏览公开页面、公开文章和公开评论 | anon 数据库角色与公开 RLS |
| 普通用户 | GitHub 登录、维护本人资料、评论、点赞、收藏、提交本人相关申请 | Supabase Auth JWT + 本人 RLS |
| 社员 | 普通用户能力、读取授权的内部资源 | profiles.role 与成员 RLS |
| 管理员 | 内容管理、知识库审核、资料变更审核、内部资源管理 | 管理员函数、RLS 与受控流程 |

界面隐藏按钮不是安全措施。数据库 RLS、约束、触发器和服务端函数是最终授权者；前端权限派生只用于改善体验。

## 4. 网站能力

### 4.1 内容与发现

- 首页和社团介绍
- 文章列表、筛选、搜索、摘要和详情
- 文章封面、标签、作者与审核状态
- 编辑入口及用户文章管理入口

文章业务数据以 Supabase Postgres 为主源；仓库中的 Markdown 主要用于静态说明和项目文档。

### 4.2 账号与资料

- Supabase Auth 承载会话
- GitHub OAuth 作为当前登录方式
- `useAuth` 统一 session、user、profile、loading 和 error
- 用户资料与认证用户 ID 一一对应
- 用户提交资料变更，管理员原子批准或拒绝

浏览器只保存 Supabase 管理的公开客户端配置和用户会话，不保存服务端特权密钥。

### 4.3 社交互动

- 文章点赞与取消点赞
- 收藏与取消收藏
- 评论读取与本人操作
- 数据库唯一约束避免重复互动
- 触发器原子维护统计数，前端不能直接覆盖计数

互动数据位于 Supabase 表中，不使用 GitHub Actions 定时同步 JSON 作为现行方案。

### 4.4 知识库

- 从文章发起知识库申请
- 普通用户只能管理与本人相关的申请
- 管理员建立知识分支并进行审批
- 跨用户读取和修改由 RLS 拒绝

### 4.5 内部资源

- 资源元数据位于数据库
- 文件位于 Supabase 私有 Storage bucket
- 普通访客和非成员被拒绝
- 社员读取，管理员上传和管理
- 文件大小边界由数据库/Storage 策略共同约束

### 4.6 管理能力

- 管理后台入口
- 文章与知识库相关管理
- 用户资料变更审核
- 角色相关入口展示

管理页面仍在后续领域组件化计划内。维护者必须同时验证 UI 和 RLS 拒绝路径。

## 5. 技术架构

```text
浏览器
  │
  ├─ VitePress 1 静态页面与文件路由
  ├─ Vue 3 组件、composable 和交互状态
  └─ @supabase/supabase-js 官方客户端
       │
       ├─ Supabase Auth：GitHub OAuth、session、JWT、自动刷新
       ├─ PostgREST：业务表访问
       ├─ PostgreSQL：数据、函数、约束、触发器、RLS
       └─ Storage：私有内部资源

GitHub 仓库
  └─ GitHub Actions → 安全检查 → VitePress 构建 → GitHub Pages
```

### 5.1 前端

- `docs/`：VitePress 内容根目录，Markdown 文件也是页面路由。
- `docs/.vitepress/config.ts`：站点、主题、导航和 Vite 配置。
- `docs/.vitepress/theme/`：布局、样式、组件和 composable。
- `theme/lib/supabase.ts`：唯一官方 SDK 客户端。
- `theme/composables/useAuth.ts`：模块级共享认证状态。
- 后续领域查询应进入 `theme/services/`，页面保持为薄路由层。

当前仍有部分早期页面包含直接查询和全局兼容调用，按 Batch 4 逐步迁移；不要复制这些旧模式到新代码。

### 5.2 数据库

`supabase/migrations/` 是新环境和变更的权威来源，按时间戳顺序覆盖：

1. profiles 与角色基础
2. articles 与文章权限
3. 点赞、收藏、评论
4. 原子互动计数
5. 知识库及申请
6. 内部资源和私有 Storage
7. 资料变更审核
8. 安全加固

`supabase/` 根目录的旧 SQL 在迁移完成前仅作兼容和历史参考，不能优先于 migrations。

### 5.3 认证链路

```text
登录页
  → Supabase signInWithOAuth(github)
  → GitHub 授权
  → Supabase OAuth callback
  → /auth/callback
  → SDK 恢复 session
  → useAuth 加载 profiles
  → 页面按 user/profile 更新
```

GitHub OAuth App 的回调必须指向 Supabase `/auth/v1/callback`；Supabase Redirect URLs 再允许本地和正式站点的 `/auth/callback`。

### 5.4 发布链路

`.github/workflows/deploy.yml` 当前使用 Node.js 22，在 `main` 推送或手工触发时：

1. `npm ci`
2. `npm run check:secrets`
3. `npm run check:security`
4. 注入公开 Supabase Variables 并执行 `npm run build`
5. `npm run check:secrets:build`
6. 上传 `docs/.vitepress/dist`
7. 发布 GitHub Pages

生成目录不进入源码管理，不允许直接编辑。

## 6. 数据与安全原则

### 6.1 密钥分级

| 类型 | 示例 | 是否可进入浏览器 | 存储位置 |
|---|---|---|---|
| 公开配置 | URL、Publishable key | 可以 | `.env.local`、GitHub Variables |
| 用户会话 | JWT、refresh token | 由 SDK 管理 | 浏览器受控存储 |
| 服务端秘密 | Secret key、service_role | 禁止 | 受控服务端或 CI Secrets |
| 外部秘密 | GitHub Client Secret、数据库密码 | 禁止 | 提供方控制台/密码管理器 |

所有 `.env*` 真实配置必须被 Git 忽略。新增环境变量时同步更新 `.env.example`，示例只写占位值。

### 6.2 RLS 与拒绝路径

- 每个业务表都必须明确启用 RLS。
- 本人操作校验 `auth.uid()` 与记录所有者。
- 管理员能力通过数据库函数和策略判断，不能信任客户端传入角色。
- 统计字段由触发器或数据库函数维护。
- 每项允许路径都应有相应匿名、跨用户或越权拒绝测试。

### 6.3 隐私与数据最小化

- 不把真实用户数据放入仓库、日志、截图和测试夹具。
- 只读取页面实际需要的 profile 字段。
- 内部资源保持私有 bucket，通过授权下载而非公开 URL。
- 离任维护者应立即撤销 GitHub、Supabase 和域名权限。

## 7. 本地开发

### 7.1 基础环境

- Node.js 22
- npm
- Git
- 数据库开发：Docker Desktop、Supabase CLI

```powershell
npm install
Copy-Item .env.example .env.local
npm.cmd run dev
```

本地公开变量：

```text
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xxx
```

### 7.2 验证矩阵

| 改动 | 最低验证 |
|---|---|
| 文档/配置 | 链接检查、`npm run build` |
| Vue/UI | 构建、相关页面、桌面与窄视口、控制台 |
| 认证 | 未登录、成功登录、刷新、过期、退出、失败回调 |
| 数据/RLS | `npm run test:db`、允许路径和拒绝路径 |
| 发布/安全 | secrets、security、build、generated secrets scan |

### 7.3 数据库重建

`npm run test:db` 负责从空库执行迁移并运行数据库测试。生产迁移前必须先在全新本地环境演练，记录迁移顺序、耗时、数据影响和回滚方法。

## 8. 项目维护手册

### 8.1 日常维护

- 每周检查 GitHub Actions、依赖告警和 Supabase 项目状态。
- 每月抽查登录、文章、互动、内部资源和管理员拒绝路径。
- 合并数据模型改动前先验证空库重建和现有数据兼容。
- 文档、Task 状态和实际行为在同一提交中保持一致。

### 8.2 发布前检查

- 工作区无调试文件、真实凭据和生成物。
- Task 已记录验证结果并单独提交。
- GitHub Variables 包含 URL 和 Publishable key。
- OAuth 的本地与正式 Redirect URLs 均已配置。
- 构建产物通过秘密扫描。
- 未经授权不执行生产迁移、部署、push 或域名变更。

### 8.3 备份与恢复

需要分别保护：Git 仓库、Supabase 数据库、Storage 文件、OAuth/域名配置和密码管理器中的恢复信息。免费计划的托管备份能力可能有限，维护者应根据 Supabase 当前套餐建立定期逻辑导出和恢复演练，不要只假设平台一定提供可用备份。

恢复顺序建议：

1. 从可信 Git 提交恢复前端和 migrations。
2. 在隔离项目执行完整迁移。
3. 恢复数据库业务数据并核对约束。
4. 恢复私有 Storage 对象和 bucket 策略。
5. 配置公开 Variables、Secrets、OAuth 与域名。
6. 执行权限矩阵和关键用户流程后再切换流量。

### 8.4 回滚

- 前端：优先使用 `git revert` 创建可审计的反向提交并重新发布。
- 数据库：每个迁移上线前单独设计向前修复或回滚脚本；禁止对生产库盲目 reset。
- 密钥泄露：立即轮换、更新受控配置、禁用旧 key，并审计 Actions 与访问日志。
- OAuth 故障：保留站点只读能力，核对 GitHub callback、Supabase provider 和 Redirect URLs。

### 8.5 常见故障

| 症状 | 首要检查 |
|---|---|
| 登录页提示配置缺失 | `.env.local`、VitePress `envDir`、GitHub Variables、重启 dev server |
| GitHub 授权后回调失败 | GitHub callback、Supabase Provider、Redirect URLs、浏览器控制台 |
| 刷新后变成未登录 | SDK session 持久化、token 刷新、系统时间、Auth 日志 |
| 页面能点但数据库拒绝 | 当前用户角色、RLS、JWT、测试环境数据 |
| 非成员看到内部资源 | 立即下线相关入口并审计 Storage/RLS；不能只修 UI |
| Pages 构建失败 | Actions 日志、Node 22、lockfile、环境 Variables、秘密扫描 |

## 9. 开发与治理

### 9.1 Task 生命周期

```text
TODO → IN PROGRESS → 实现 → 验证 → DONE → 独立本地 commit
```

任务负责人负责整合产品、前端、数据安全和发布验证，不把集成责任留给下一位维护者。生产变更、付费、凭据、部署、push 和 PR 等外部操作必须有明确授权。

### 9.2 代码放置

- 新数据访问代码进入 `theme/services/`。
- Supabase 单例和共享设施进入 `theme/lib/`。
- 数据库类型进入 `theme/types/`。
- Markdown 页面保持薄层，不继续堆积查询和复杂状态。
- 新迁移进入 `supabase/migrations/`，并保持可重复执行和可测试。

### 9.3 架构决策

重大选择使用 ADR 记录背景、选择、备选方案、影响和重新评估条件。当前基线是 VitePress + Vue + Supabase + GitHub Pages；若要迁移平台、替换数据主源或改变认证边界，必须新增 ADR。

## 10. 交接清单

接任者应取得但不要在仓库记录以下权限：

- GitHub 仓库管理员、Pages 和 Actions 管理权
- Supabase 组织/项目权限与账单联系人
- GitHub OAuth App 管理权
- 自定义域名与 DNS 管理权（如启用）
- 密码管理器中的数据库恢复凭据和密钥轮换记录

交接演练至少完成：

1. 在新电脑安装依赖并启动站点。
2. 从空库执行全部 migrations 和 tests。
3. 使用测试账号验证普通用户、社员、管理员及拒绝路径。
4. 在不接触生产秘密的情况下完成一次预览构建。
5. 演练前端回滚、密钥轮换和数据库恢复流程。
6. 核对 DevPlan 中所有 `IN PROGRESS`、阻塞项和未推送提交。

## 11. 路线图

- 完成统一认证的真实 OAuth 验收

## 12. 维护责任

白皮书不是一次性报告。出现以下变化时必须更新：产品能力上线/取消、角色权限变化、数据主源变化、环境变量变化、Node/依赖基线变化、部署链路变化、域名/OAuth 变化、备份恢复策略变化或新的重大架构决策。

维护者最终要保证三件事一致：**用户实际看到的行为、代码和数据库实际执行的规则、文档对现状的描述**。
